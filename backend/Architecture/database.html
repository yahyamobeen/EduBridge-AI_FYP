Authentication is application-managed — FastAPI issues its own JSON Web Tokens (JWTs) and hashes passwords with argon2id. Supabase Auth (auth.users) is deliberately unused, so auth.uid() does not exist here. Every policy instead reads a transaction-scoped session setting through app.current_user_id(), bound by SELECT set_config('app.current_user_id', :uid, true) at backend/app/core/db.py:33-59.

The entity-relationship diagrams below are clustered one per domain — 46 tables cannot render legibly in a single diagram, and the point of a diagram is to be read. The complete field lists, the full policy catalogue with every USING and WITH CHECK predicate, the invariants and the known gaps live in database.md, which is the authoritative page; this one is its visual companion.

The second authorization layer does not currently hold User-story card 1.5 promises that each request is "checked by the application and again by the database, so that a single missed check can never expose another student's data." That is false today. Most write policies are FOR ALL with ownership as the only predicate, grants are table-wide so Row-Level Security gives no column protection, and one view bypasses Row-Level Security entirely. The application layer is holding alone. All nineteen findings are catalogued in Known gaps — they are defence-in-depth failures, not remote exploits, because reaching them requires arbitrary SQL as app_backend and every implemented route is narrow.

The default-partition trap A partitioned table's primary key must include the partition key, which is why both are (id, created_at). More importantly: the blanket enable-and-force loop at 20260801120100:126-137 filters tablename NOT LIKE '%_default', which left both DEFAULT partitions with Row-Level Security disabled entirely. ENABLE ROW LEVEL SECURITY does not cascade to partitions and policies are per-table, so an app_backend connection could run SELECT * FROM public.audit_log_default and read the whole audit trail straight past audit_admin_read. Fixed by 20260802150000:35-38. Every future partition needs the same two ALTER TABLE statements.

audit_log is append-only from the application: audit_insert plus audit_admin_read, and no UPDATE or DELETE policy at all, so under forced Row-Level Security the trail cannot be edited or erased through app_backend. The tamper-resistance is the absence of policies, which means it is silently destroyed by anyone who adds a FOR ALL policy to tidy up.

The app.* privileged functions — 33 live

34 distinct names were ever defined; app.issue_token_for_email was dropped as a byte-for-byte duplicate of app.insert_auth_token 20260803160000:151-153. Of the 37 definition statements, 35 are SECURITY DEFINER and 36 carry SET search_path = public, pg_temp — the exceptions being the trigger function and, for the definer count, app.current_user_id(). None takes dynamic SQL. Full signatures, return types, call sites and grants are in database.md.

Why these exist at all Login, refresh, email verification, password reset, two-factor enrolment and the guardian flow all run before a session exists — there is no app.current_user_id() to satisfy an owner-scoped policy with. The alternative was to connect as the Row-Level-Security-bypassing service role, but then the bypass is implicit in a connection and spreads. These functions make the exception explicit, auditable and narrow: each returns only the columns its flow needs 20260802140000:96-110. The standing rule is to add another narrow function, never to widen the door.

Migration rules

RuleWhy
Filename is YYYYMMDDHHMMSS_snake_case_description.sqlMigrations run in filename order, so the timestamp prefix is a dependency declaration, not decoration. supabase migration new <name> generates it.
Never edit an applied migration — add a new oneThe files and the applied database can diverge and have: 20260803090000:12-22 records a live path that failed silently because the applied guardian_link_update was parent-only while the file said either participant. Read pg_policies, not the file, for what is live.
Make every migration re-runnableThe Supabase command-line interface does not wrap a migration file in a transaction. A part-way failure leaves earlier statements committed and the migration unrecorded, and the obvious retry then dies on "policy already exists". DROP POLICY IF EXISTS before every CREATE POLICY — PostgreSQL has no CREATE POLICY IF NOT EXISTS.
A changed RETURNS TABLE needs drop-then-createRETURNS TABLE columns are OUT parameters, so adding one changes the return type and PostgreSQL refuses: "cannot change return type of existing function" (SQLSTATE 42P13). 20260803160000:94-104.
Adding a parameter is worse, because it fails quietlyCREATE OR REPLACE does not replace a different arity — it overloads. Without the explicit drop, both activate_2fa(uuid) and activate_2fa(uuid, bigint) would exist and a one-argument call would match both, failing at runtime with "function name is not unique". 20260803160000:70-76.
A drop takes its grant and its comment with itDROP FUNCTION silently removes the GRANT EXECUTE and the COMMENT ON FUNCTION. Every drop-and-recreate must re-issue REVOKE ALL … FROM PUBLIC, GRANT EXECUTE … TO app_backend and the comment. Forget it and the function survives with the default EXECUTE to PUBLIC — the silent version of finding C5. 20260803160000:158-179.
A new enum value gets its own filePostgreSQL will not let a value added by ALTER TYPE … ADD VALUE be used in the same transaction, and the CLI runs each migration as one. 20260802140100_token_kind_enrollment.sql adds one value and does nothing else.
A new table needs four things, not oneENABLE, FORCE, at least one policy (or a deliberate comment saying why none), and — if partitioned — steps 1 and 2 repeated on every partition including the default. Grants are forward-looking; enablement is not (finding B19).
The agent never pushes a migrationIt produces the file, verifies it with a dry run against a shadow or branch database, and reports the real output. The repository owner applies it.
One manual step the migrations cannot do app_backend is created NOLOGIN with no password, because passwords are never committed. Set it once, out of band, with ALTER ROLE app_backend WITH LOGIN PASSWORD '<strong-password>'; and point DATABASE_URL at that role, not postgres. Connecting as postgres bypasses Row-Level Security and makes every policy on this page inert — which is why backend/app/core/db.py:119-164 refuses to start when it detects rolsuper or rolbypassrls.

Connecting from FastAPI

The codebase is entirely synchronous SQLAlchemy — Session, db.execute, sessionmaker. There is no AsyncEngine, no async with engine.begin() and no await on a database call anywhere.

from sqlalchemy import text
from sqlalchemy.orm import Session

def set_current_user_id(session: Session, user_id: UUID | str) -> None:
    parsed = UUID(str(user_id))
    session.execute(
        text("SELECT set_config('app.current_user_id', :uid, true)"),
        {"uid": str(parsed)},
    )

set_config(..., is_local => true) is the parameterised equivalent of SET LOCAL, which cannot take a bind parameter and would otherwise have to be built by string concatenation. Verbatim at backend/app/core/db.py:33-59.

A stray commit() silently unbinds the user The setting is transaction-scoped. A commit() mid-request ends the transaction and discards it; every query after that runs with no user bound and returns zero rows with no error raised anywhere. If you are chasing a "the query returns nothing but the row is definitely there" bug, look for a stray commit first. backend/app/core/db.py:45-50.
